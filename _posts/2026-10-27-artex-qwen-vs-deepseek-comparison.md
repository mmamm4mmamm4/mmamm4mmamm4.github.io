# ARTEX LLM 비교: 로컬 Qwen3.8 27B vs DeepSeek V4.1 Flash

같은 대상(`192.168.6.167`, 모두뱅크 웹 애플리케이션)과 같은 작업 목표로 ARTEX를 두 번 실행한 결과를 나란히 두고 봅니다. 두 실행은 LLM이 주된 차이지만, worker 수(4개 대 3개)와 실행 방식(로컬 대 호스팅), 컨텍스트 설정도 함께 달랐고 서버 상태를 같게 맞춘 것도 아닙니다. 그래서 통제된 모델 교체 실험이 아니라 두 번의 실행을 대조한 기록으로 읽어 주시기 바랍니다. 발견 사항은 각 실행의 ARTEX 최종 보고서 기준이고(두 실행 모두 요청을 수동으로 재현하지는 않았습니다), 토큰·호출·시간 같은 수치는 kali_mcp로 확인한 ARTEX 트랜스크립트(`exp1-*`, `exp4-*`)에서 제가 집계한 값입니다.

## 비교 조건

| 항목 | Qwen3.8 27B (exp1) | DeepSeek V4.1 Flash (exp4) |
|---|---|---|
| 실행 위치 | 집 PC Ollama `qwen38-27b`(iq3_m 양자화, RTX 5070 Ti 16GB) | OpenRouter `deepseek/deepseek-v4.1-flash` |
| ARTEX 컨텍스트 설정 | `context_window_k`=32(약 32768 토큰) | 설정값 미확인(모델 최대는 약 1M 토큰) |
| ARTEX 구성 | planner 1 + worker 4(i3~i6) | planner 1 + worker 3(i57~i59) |

두 실행은 독립 조건이 아닙니다. Qwen 실행이 먼저였고, DeepSeek 실행은 그 뒤에 같은 서버를 대상으로 돌았습니다. DeepSeek의 worker 하나가 "포트 정보가 다른 작업(task 1, 3)에서 발견된 것"이라고 기록한 점으로 보아 ARTEX가 자산 그래프를 작업 사이에 공유하는 것으로 보입니다. 다만 planner가 받은 관련 작업 목록(`related_tasks`)은 비어 있었고, 이전 실행의 발견 사항이 그대로 전달된 흔적은 확인하지 못했습니다. 이 공유가 결과에 얼마나 영향을 줬는지는 측정하지 못했으므로 잠재적 교란 요인으로만 둡니다. 실행 횟수도 모델당 1회라 우연에 따른 편차를 배제할 수 없습니다.

## 실행 지표

| 지표 | Qwen3.8 27B | DeepSeek V4.1 Flash |
|---|---|---|
| 트랜스크립트 시간 범위 | 01:44:57 ~ 04:39:14 UTC(약 2시간 54분, 32K 컨텍스트 적용을 위한 중단·재개가 끼어 있어 순수 탐색 시간이 아님) | 07:18:19 ~ 07:21:00 UTC(약 3분, 최종 보고서는 시작 후 약 4분에 생성) |
| LLM 호출 | 105회 | 64회 |
| 입력 / 출력 토큰 | 약 152만 / 약 5.0만 | 약 134만 / 약 4.5만 |
| 호출당 최대 입력 | 21,458 | 40,236 |
| 컨텍스트 압축 | 3회(worker별 약 19~21K에서 1회씩) | 0회 |
| Bash 실행 | 119회 | 74회 |
| 비용 | API 비용 없음(로컬 전력만) | 목록가 기준 약 0.21달러 |

DeepSeek 비용은 OpenRouter 목록가(입력 100만 토큰당 0.14달러, 출력 0.42달러)로 계산한 추정치입니다. 실제 차감액은 OpenRouter Activity 화면에서 확인해야 합니다. 이 실행 전에 같은 모델로 두 번(exp2·exp3) 시도했는데, 계정 잔액 부족으로 OpenRouter가 `402`를 반환해 중단됐습니다. 이 두 번의 토큰 사용량은 위 표에 넣지 않았습니다.

## 발견 사항 비교

| 취약점 | Qwen3.8 27B | DeepSeek V4.1 Flash |
|---|---|---|
| `/bank/connectivity/check` OS 명령 주입(tomcat 명령 실행) | 발견 | 미발견 |
| `/admin` 접근 통제 누락과 평문 비밀번호 노출 | 발견 | 미발견 |
| `MODU_SID` 순차 정수로 다른 계정 사칭 | 발견 | 발견 |
| `/files/upload` 웹루트 업로드로 JSP 실행 | 엔드포인트만 후보로 언급(업로드 RCE 근거 없음) | 발견 |
| Tomcat Manager `admin:tomcat`과 WAR 배포 | 미발견 | 발견 |
| `/files/download` 경로 순회로 파일 읽기 | 엔드포인트만 후보로 언급 | 발견 |
| AJP(8009) Ghostcat | 클라이언트 구현 실패로 판단 못함 | 언급만 하고 검증 안 함 |
| root 권한 상승 | 시도 기록 없음 | SUID 바이너리로 시도했으나 실패 |

ARTEX 보고서 기준 건수는 Qwen 5건, DeepSeek 4건입니다. Qwen 보고서는 같은 취약점이 중복 등록돼, 중복을 묶으면 3개 유형입니다. DeepSeek 보고서 4건은 중복이 없습니다. 두 실행 모두 tomcat(uid 990) 권한의 명령 실행까지 도달했지만 경로가 달랐습니다. Qwen은 명령 주입, DeepSeek은 업로드와 Manager 배포로 도달했습니다. 두 결과를 합치면 서로 다른 취약점은 6개 유형입니다.

## 동작 차이

Qwen은 정찰과 페이지 수집 기록이 많았습니다. AJP 확인에서는 Python 클라이언트를 네 번 고쳐 쓰고도 패킷 형식을 맞추지 못했고, 모델이 Ghostcat의 CVE 번호를 잘못 적은 일도 있었습니다. 자산은 "ip 1, service 1"로 등록됐는데, 열린 포트가 4개인 점과 대비됩니다. 다만 ARTEX의 자산 집계 기준을 확인하지 않아, 이것이 등록 누락인지 집계 방식 차이인지는 단정하지 않습니다.

DeepSeek은 기본 자격 증명 대입처럼 결과가 바로 확인되는 요청이 초반에 있었습니다. 한 worker(i57)가 짧은 시간에 네 가지를 연달아 확인한 뒤 권한 상승까지 시도했습니다. 자산은 "app 1, endpoint 9, ip 1, root_domain 1, service 4"로 등록됐습니다. planner가 목표 달성을 선언한 뒤 나머지 worker를 바로 종료했고, Qwen이 찾은 명령 주입과 `/admin` 노출은 이 보고서에 없습니다. 이 둘이 종료 때문에 탐색되지 않은 것인지, 탐색했으나 보고에서 빠진 것인지는 트랜스크립트로 확인하지 않았습니다.

## 대상 서버에 남은 흔적

- Qwen 실행: `/admin` 응답에 나타난 계정 `hk1793071789`, `hkprobe1`(ARTEX가 테스트 중 만든 것으로 보이나 가입 과정은 확인 못 함)
- DeepSeek 실행: 업로드한 `i57shell.jsp`, 배포한 `/pwn57` 애플리케이션, 로그인에 쓴 계정 `hacker57`

다음 비교 전에는 VM을 스냅샷으로 되돌려 두 실행이 같은 상태에서 시작하도록 맞춰야 합니다.

## 정리

이번 비교에서 확인된 점은 두 가지입니다. 첫째, DeepSeek V4.1 Flash 실행은 외부 API 요금 추정 약 0.21달러(실제 차감액은 미확인)로 중복 없는 4건을 보고했고, 최종 보고서가 시작 후 약 4분에 생성됐습니다. 로컬 Qwen3.8 27B 실행은 외부 API 요금은 없었고(로컬 전력·장비 비용은 별도) 중단·재개를 포함해 약 3시간이 걸렸으며, 중복을 묶으면 3개 유형을 보고했습니다. Qwen 쪽 시간에는 설정 변경 중단이 끼어 있어 두 시간을 모델 속도 차이로 바로 읽기는 어렵습니다. 둘째, 두 보고서가 겹친 취약점은 `MODU_SID` 하나뿐이고, 나머지는 서로 달랐습니다. 다만 한쪽 보고서에 없는 항목이 곧 그 모델의 탐지 실패를 뜻하지는 않습니다. 범위는 단일 랩 호스트에서 모델당 1회 실행한 결과이고, 실행 순서·worker 수·공유 자산 그래프 같은 교란 요인이 섞여 있습니다. 또 발견 건수는 모두 ARTEX 최종 보고서 기준이며, 두 실행 다 요청을 수동으로 재현해 확정한 것은 아닙니다. 다음 비교는 스냅샷 복원 후 실행 순서를 바꾸거나 같은 모델을 반복 실행해 편차를 확인하는 방식으로 진행할 예정입니다.
