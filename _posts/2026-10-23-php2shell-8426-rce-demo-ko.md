# PHP session.upload_progress OOM Use-After-Free 원격 코드 실행 (CVE-2026-109618 / CVE-2026-109619)

## 개요

PHP의 `session.upload_progress` 기능에서 멀티파트 업로드 처리 중 메모리 부족(OOM)이 발생할 때, 세션 수명주기가 정상적으로 닫히지 못하고 전역 포인터가 매달린 채 다음 요청으로 넘어가는 Use-After-Free 결함입니다. 인증 없이 HTTP 요청만으로 ASLR을 우회해 원격 코드 실행까지 이어지며, 공식 심각도는 CVSS v4.0 9.2(Critical)로 부여돼 있습니다.

이 글은 격리된 로컬 Docker 랩에서 PHP 8.4.26(공식 `php:8.4.26-apache`, Apache mod_php 단일 prefork 워커) 대상으로 해당 결함을 재현하고, 실제로 웹 서버 권한(`www-data`) 명령 실행에 도달하는 과정을 확인한 기록입니다. 취약점의 동작 원리와 원인, 그리고 대응에 초점을 두며, 재현에 사용한 익스플로잇 코드·오프셋·페이로드 세부는 공개하지 않습니다.

영향 범위는 공식 권고 기준으로 PHP 5.4.0부터 8.5.11까지의 모든 브랜치이며, 2026-10-21 공개된 8.5.12 / 8.4.27 / 8.3.36 / 8.2.35에서 수정됐습니다. 역시 공식 권고 기준으로 웹 요청을 처리하는 모든 SAPI가 영향권이지만, 단일 프로세스 상태가 요청 간 유지되는 Apache mod_php 구성에서 위험이 가장 높습니다. 이 글의 재현과 확인 범위는 그중 8.4.26 / mod_php 한 구성에 한정합니다.

## 취약점 분석

취약점의 핵심은 세션 업로드 진행률 추적 경로에 있습니다. 공격은 세 가지 조건을 엮습니다.

첫째, 세션 활성화입니다. 멀티파트 본문에 `PHP_SESSION_UPLOAD_PROGRESS` 필드와 공격자가 지정한 세션 식별자를 함께 보내면, PHP가 업로드 진행 상황을 세션에 직렬화하기 시작합니다. 이 과정에서 세션 관련 전역 상태(`PS(id)`, `PS(http_session_vars)`)가 요청 처리 중 할당된 세션 객체를 가리키게 됩니다.

둘째, 수명주기 중단과 전역 포인터 잔존입니다. `memory_limit`를 넘기도록 큰 멀티파트 본문을 보내 파싱 도중 OOM을 유발하면, PHP 내부가 `zend_activate_modules()` 이전 시점에서 `longjmp`로 빠져나갑니다. 그 결과 요청 종료 시 호출돼야 할 `RSHUTDOWN`(세션 모듈 정리 포함)이 건너뛰어지고, 위 세션 전역 상태가 이전 요청에서 가리키던 포인터 값을 정리되지 않은 채 그대로 보존합니다. 단일 워커가 프로세스를 유지하므로 이 전역 포인터는 다음 요청까지 살아남습니다.

셋째, 재점유와 제어 흐름 탈취입니다. 다음 요청이 세션을 다시 초기화·처리하는 과정에서, 매달린 전역이 가리키던 세션 객체 영역은 해제·재사용 대상이 됩니다. 이때 공격자가 같은 크기의 힙 청크로 그 자리를 다시 채우면, 전역 포인터가 공격자 데이터를 가리키는 Use-After-Free가 성립합니다. 재현 과정에서 관찰된 흐름은 (1) 세션 응답에 섞여 나오는 힙 포인터로 ZendMM 청크 베이스를 누출하고, (2) HashTable 정렬을 이용해 `libphp.so` 베이스를 계산한 뒤, (3) 재점유한 객체 안에 가짜 소멸자 포인터를 심어, 세션이 해제되는 시점에 원하는 함수가 호출되도록 유도하는 순서였습니다. 이 세 단계의 앞에는 대상 워커를 선점하는 준비 요청이 놓입니다. 최종적으로 웹 서버 권한의 명령 실행에 도달합니다.

## 원인

근본 원인은 세션 업로드 진행률 핸들러가 요청 경계를 넘어 유효하지 않게 되는 포인터에 의존했다는 점입니다. OOM에 의한 `longjmp`가 정상적인 모듈 종료 단계를 건너뛰면서, 세션 전역 상태가 이전 요청의 포인터를 정리하지 못한 채 보존합니다. 다음 요청에서 그 전역이 가리키던 세션 객체가 해제·재배치되면, 남아 있던 포인터가 더 이상 유효하지 않은 메모리를 참조하게 되어 Use-After-Free가 성립합니다.

공식 수정과 동봉 패치가 바로잡는 지점도 동일합니다. 업로드 진행률 구조에서 버킷 포인터를 캐싱하던 필드(`post_bytes_processed`, `current_file_bytes_processed`)를 `zval *`에서 `zend_long` 원시값으로 바꿔, 요청 간 살아남을 수 있는 포인터 자체를 없앴습니다. 또한 매 업데이트마다 세션 엔트리를 다시 조회하도록 바꿔, 중간에 재배치된 메모리를 오래된 포인터로 건드리지 않게 했습니다. 즉 결함은 "특정 입력이 만드는 버그"라기보다, 비정상 종료 경로에서 정리되지 않는 포인터 수명 관리의 문제였습니다.

한 가지 분명히 할 점은 설정 의존성입니다. 이 경로가 성립하려면 `session.upload_progress.enabled`가 켜져 있어야 하고(다수 배포판 기본값), OOM을 일으킬 수 있도록 `memory_limit` 대비 본문 크기가 충분해야 합니다. 재현 랩에서 버전이 맞아도 이 OOM 유발 조건이 어긋나면 1단계 정보 누출부터 성립하지 않았습니다.

## 대응 방안

가장 확실한 조치는 수정 버전으로의 업그레이드입니다. PHP 8.5.12 / 8.4.27 / 8.3.36 / 8.2.35 이상으로 올리면 근본 원인이 제거됩니다. 랩에서도 동일 조건의 8.4.27 패치 빌드에서는 정보 누출 단계가 재현되지 않았으며, 이는 패치가 매달린 포인터 경로를 없앴다는 설명과 부합합니다(범위: 로컬 Docker 랩).

즉시 적용 가능한 완화는 다음과 같습니다.

- `session.upload_progress.enabled = Off` — 이 글에서 다룬 업로드 진행률 진입 경로를 직접 차단합니다. 진행률 표시 기능을 쓰지 않는 환경이라면 비용이 낮은 조치입니다.
- `memory_limit`·`post_max_size` 점검 — 비정상적으로 작은 `memory_limit`은 OOM 유도를 쉽게 만듭니다. 운영 값과 업로드 한도를 함께 재검토합니다.
- 배포판 백포트 확인 — Debian·Ubuntu·RHEL 등은 버전 문자열을 바꾸지 않고 수정을 백포트하는 경우가 있습니다. 상태 판단은 `php -v`가 아니라 벤더 보안 권고(USN/DSA/RHSA 등)의 패키지 버전으로 하는 편이 안전합니다.
- 컨테이너 이미지 재배포 — 공식 `php` 이미지는 업스트림 버전을 따르므로, 고정 태그(예: `php:8.4.27-apache`)에서 다시 빌드·배포합니다.

탐지 관점의 보완책으로, 요청 특징 기반 WAF 룰도 유효합니다. 재현 트래픽에서 반복적으로 관찰된 신호는 ① 멀티파트 본문에 `PHP_SESSION_UPLOAD_PROGRESS` 필드와 `PHPSESSID`가 폼 필드 형태로 함께 나타나는 조합, ② 한 요청의 멀티파트 파트 수가 비정상적으로 많은 경우, ③ 텍스트 폼 필드 값에 NUL·포인터성 바이너리가 섞인 경우입니다. 다만 세션 ID를 폼으로 전달하는 정상 구현도 존재하므로 ①은 단독 지표보다 다른 신호와 결합해 쓰는 편이 안전하며, 이들 특징은 본 완화(패치·설정)를 대체하지 못하는 보완 통제입니다. 우회를 고려하면 고정 boundary 같은 단일 상수보다 프로토콜 의미 기반 조건에 거는 편이 견고합니다.

## 정리

이번 재현에서 확인된 것은 두 가지입니다. 첫째, `session.upload_progress`가 켜지고 OOM 유발 조건이 맞는 PHP 8.4.26 구성에서 이 결함은 인증 없이 웹 서버 권한의 원격 코드 실행까지 이어졌습니다(범위: 로컬 Docker 랩, 시연 영상으로 `www-data` 명령 실행 확인). 둘째, 동일 Apache 버전에 PHP만 8.4.27로 올린 패치 빌드에서는 1단계 정보 누출부터 성립하지 않았습니다. 이는 수정이 해당 경로를 제거했다는 설명과 부합하는 거동이며, 코드 레벨의 원인 제거를 직접 입증한 것은 아니라는 점은 분명히 해 둡니다.

운영 환경에서의 우선순위는 명확합니다. 수정 버전 업그레이드가 먼저이고, 그 전까지는 `session.upload_progress.enabled=Off`가 비용이 낮은 차단책입니다. 다음 작업으로는 ASan 계측 빌드에서 OOM 직후의 Use-After-Free 시점을 오라클로 직접 포착해, 패치의 차단 여부를 코드 레벨에서 교차 확인하는 방향이 남습니다.
