# ARTEX 자동 침투 결과: 192.168.6.167 모두뱅크 웹 애플리케이션

이전 정찰 단계에서 대상으로 확정한 피해자 서버 `192.168.6.167`에 ARTEX를 실행해, 자동 침투 테스트로 취약점을 찾은 결과를 기록합니다. ARTEX에 준 작업 목표는 "192.168.6.167 단일 ip 대상으로 취약점 찾아줘. 쉘 권한까지 획득 할 수 있으면 진행해줘."입니다. 최종 보고서는 ARTEX 기준 2026-10-27 04:42:11에 생성됐습니다.

출처는 두 가지입니다. PoC와 응답은 ARTEX 최종 보고서에서 옮겼습니다. 환경, worker 활동, 정찰 내용과 미확인 항목은 kali_mcp로 Kali의 ARTEX 트랜스크립트(`data/transcripts/*.jsonl`)와 작업 파일(`data/tasks/1/`)을 직접 확인한 결과입니다. 요청을 수동으로 재현하지는 않았습니다.

## 환경

- 공격 측: VMware Kali `192.168.6.132`. ARTEX(`~/mma/artex-ko-plus`)가 같은 Kali에서 동작합니다.
- LLM: 집 PC Ollama의 `qwen38-27b`. 모델 컨텍스트는 32768 토큰이고, ARTEX 프로필 `context_window_k`는 32입니다. 작업 중 worker 세션이 약 19–21K 토큰에서 한 번씩 압축됐고, 압축 뒤에도 작업은 이어졌습니다.
- 에이전트 구성: planner 하나가 intent를 만들고 intent마다 worker가 하나씩 붙었습니다. 트랜스크립트에 남은 worker는 i3·i4·i5·i6 네 개입니다. 주로 활동한 worker는 셋으로, i3는 웹 페이지 수집, i4는 인증과 관리자 기능, i5는 AJP(8009)를 맡았습니다. i6은 늦게 시작돼 기록이 짧습니다.
- 대상: `192.168.6.167`. 노출 서비스는 OpenSSH 9.9, nginx 1.20.1(80), AJP13(8009), Apache Tomcat(8080)입니다. 80과 8080 모두 Spring Boot 앱 `modubank`(모두뱅크, 패키지 `kr.co.modubank`)를 서비스합니다. 앱 페이지에 "Command Injection 훈련용"이라는 문구가 있어, 의도적으로 만든 취약 앱으로 보입니다.

## 정찰

worker들은 처음에 Spring Boot Actuator를 확인했습니다. 인증 없이 `/actuator/env`(`env.json`)와 `/actuator/mappings`(`mappings.json`)를 받을 수 있었습니다. 다만 `env`의 값은 `******`로 가려져 있어 Java·OS 버전 같은 정보는 얻지 못했습니다. 엔드포인트는 `mappings`로 파악했고, 다음 경로를 찾았습니다.

- `/admin`
- `/files/upload`, `/files/download`
- `/bank/connectivity/check`

로그인, 회원가입, 게시판, 이체, 상품 페이지도 함께 수집했습니다.

## 발견 사항

ARTEX 보고서에는 5건이 올라 있습니다. 엔드포인트와 원인이 같은 항목을 하나로 묶으면 3개 유형이 됩니다. 1번과 2번은 같은 파라미터의 명령 주입입니다. 3번과 4번은 같은 `/admin` 페이지를 80번과 8080번 포트로 각각 요청한 결과입니다. 5번은 따로 남습니다. 80번과 8080번이 같은 구현인지는 확인하지 않았습니다.

### OS 명령 주입: `/bank/connectivity/check` (CRITICAL)

"서버 상태 확인" 기능은 `host` 파라미터를 받아 ping을 실행합니다. 이 값이 자유 입력이고, `;`나 줄바꿈(`\n`) 뒤에 붙인 명령이 그대로 함께 실행됩니다. 입력 검증이 이 문자들을 걸러 내지 못하고 있습니다.

```bash
curl -sS -b 'MODU_SID=1006' --get --data-urlencode 'host=192.168.6.167;id' \
  'http://192.168.6.167/bank/connectivity/check'
```

```
uid=990(tomcat) gid=990(tomcat) groups=990(tomcat) context=system_u:system_r:unconfined_service_t:s0
```

줄바꿈으로 주입했을 때도 `whoami`는 `tomcat`, `id -u`는 `990`, `pwd`는 `/`로 출력됐습니다. 백틱(`` ` ``)으로도 명령이 실행됐지만, 결과가 ping 인자 안에 들어가 별도 줄로 나오지는 않았습니다. ARTEX는 이 주입이 인증 없이 동작한다고 기록했습니다. 그러나 PoC 요청에는 모두 `MODU_SID` 쿠키가 붙어 있어, 쿠키 없이 확인한 기록은 없습니다.

SELinux 컨텍스트는 `unconfined_service_t`입니다. 이름으로 보면 제한이 약한 도메인이지만, enforcing 여부와 적용된 정책은 확인하지 않았습니다. ARTEX 보고서의 1번과 2번이 이 건입니다.

### 관리자 페이지 접근 통제 누락과 평문 비밀번호 노출 (HIGH)

`/admin`은 관리자 전용 페이지입니다. 그런데 역할이 `USER`인 일반 사용자 세션(`MODU_SID=1006`, 홍길동)으로 요청해도 200이 반환됩니다.

```bash
curl -sS -b 'MODU_SID=1006' http://192.168.6.167/admin
```

80번 포트 응답에는 전체 사용자의 아이디, 평문 비밀번호, 이름, 역할과 계좌 잔액이 표시됐습니다(ARTEX 보고서 3번).

```
1 admin   admin123    시스템관리자 ADMIN
2 kim01   password1   김민준       USER
3 lee02   qwer1234    이서연       USER
4 park03  letmein     박도윤       USER
5 sec01   Test@12345  Sec          USER
6 hk1793071789  Test1234!
7 hkprobe1      Test1234!

110-234-567890 (소유 2) 5,000,000
110-345-678901 (소유 3) 12,000,000
110-456-789012 (소유 4)    800,000
```

8080번 포트의 `/admin`에 같은 쿠키로 직접 요청해도 USER 권한으로 접근할 수 있었습니다(ARTEX 보고서 4번). 다만 이 응답에 기록된 것은 1~5번 계정의 평문 비밀번호뿐이고, 6·7번 계정과 계좌 잔액은 없습니다. 6·7번은 ARTEX가 테스트 중 회원가입으로 만든 계정으로 보여, 8080 요청이 계정 생성보다 먼저였을 가능성이 있습니다.

비밀번호가 응답에 평문으로 노출된다는 점은 확인했습니다. DB에도 평문으로 저장돼 있는지는 저장소나 구현을 보지 않아 확인하지 못했습니다.

### `MODU_SID` 쿠키만으로 다른 사용자 사칭 (HIGH)

서버는 클라이언트가 보낸 `MODU_SID` 값(숫자 사용자 ID)을 검증 없이 현재 사용자로 사용합니다. `JSESSIONID` 없이 `MODU_SID` 하나만 보내도 로그인 상태가 됩니다. ARTEX는 `1001`~`1007`로 값을 바꿔 각 사용자로 전환했다고 기록했습니다. 반대로 `0`, `-1`, `1`~`40`, `999999`에는 200이 아닌 응답이 왔습니다. 작업 파일에는 `dash_1001.html`~`dash_1005.html` 다섯 개의 대시보드 응답이 남아 있습니다. `1006`은 PoC 전체에 쓰인 세션입니다. `1007`의 응답 파일은 없습니다.

ID가 순차적인 숫자라 추측하기 쉽습니다. 앞의 `/admin` 노출과 합치면, 로그인 없이 쿠키 하나로 모든 계정의 비밀번호를 얻을 수 있습니다. ARTEX 보고서의 5번이 이 건입니다.

### 확인하지 못한 항목

- AJP(8009): i5가 Python으로 AJP 클라이언트를 네 번(`ajp.py`~`ajp4.py`) 고쳐 썼습니다. 하지만 패킷 길이 필드가 틀려 서버 응답을 받지 못했습니다. 그래서 Ghostcat(CVE-2020-1938) 해당 여부는 판단하지 못했습니다. 작업 중 모델이 이 취약점의 번호를 CVE-2022-42889로 잘못 적은 일도 있습니다.
- `/files/upload`, `/files/download`: i4가 경로 조작 후보로 올렸지만, 보고서에는 결과가 없습니다.
- 셸: 명령 실행까지만 확인했습니다. 트랜스크립트 전체에서 `bash -i`, `/dev/tcp`, `nc -e`, `mkfifo` 같은 리버스 셸 명령을 검색했지만 나오지 않았습니다. 대화형 셸과 권한 상승은 시도하지 않은 것으로 보입니다. 작업 목표의 "쉘 권한"은 tomcat 권한의 명령 실행까지만 달성됐습니다.

## ARTEX 동작 관찰

- 이번 보고서는 자산을 "ip 1, service 1"로 집계했습니다. 열린 포트는 4개인데 service는 1개입니다. 집계 기준을 확인하지 않아 등록 누락인지는 단정하지 않습니다.
- 이번 최종 보고서에는 같은 엔드포인트의 항목이 두 쌍 중복으로 남아 있습니다.
- 32K 창에서 압축이 일어난 뒤에도, worker들은 대상과 앞서 찾은 내용을 유지한 채 작업을 이어 갔습니다.

## 정리

이번에 확인된 핵심은 두 가지입니다. 첫째, `/bank/connectivity/check`의 명령 주입으로 tomcat(uid 990) 권한의 원격 명령 실행이 가능합니다. 둘째, `MODU_SID` 사칭과 `/admin` 노출을 합치면 로그인 없이 전체 계정의 평문 비밀번호를 얻을 수 있습니다. 범위는 로컬 랩 NAT 대역의 단일 호스트입니다. 응답 근거는 ARTEX 기록이고, 수동 재현은 아직 하지 않았습니다. 다음 단계는 같은 요청을 수동으로 재현하면서, 각 요청이 nginx·Tomcat 접근 로그와 `/var/log/secure`에 어떻게 남는지 대조해 탐지 시나리오를 만드는 것입니다.
