# Artex·Cyberstrike 공격 트래픽 비교 분석 (modubank 192.168.6.167)

두 개의 패킷 캡처(`artex.pcapng`, `cyberstrike.pcapng`)를 각각 분석하고, 두 공격 세션의 성향 차이와 공격 중에 섞여 흐른 정상 트래픽을 정리한 기록입니다. 분석은 Wireshark `tshark`/`capinfos`로 프로토콜 계층·엔드포인트·HTTP 통계·TLS SNI·DNS 질의를 뽑아 교차 확인하는 방식으로 진행했습니다.

## 대상과 환경

두 캡처 모두 같은 날(2026-11-12), 같은 타깃과 같은 공격자 사이의 트래픽입니다.

- 타깃: `192.168.6.167` (modubank 웹 애플리케이션, RockyLinux 9 / Tomcat)
- 공격자: `192.168.6.132` (Kali)
- Artex 세션: 15:23:05 ~ 15:41:49 KST (약 18.7분)
- Cyberstrike 세션: 16:02:43 ~ 16:18:58 KST (약 16.3분)
- 두 세션 간격은 약 21분으로, 동일 타깃에 대한 연속 작업으로 보입니다.

## 캡처 개요

| 항목 | Artex | Cyberstrike |
|---|---|---|
| 총 패킷 | 385,569 | 103,909 |
| 데이터 크기 | 248 MB | 96 MB |
| 캡처 시간 | 1,124초 | 975초 |
| TLS 바이트 | 약 90 MB | 약 54 MB |
| HTTP 프레임 | 1,960 | 11,898 |
| AJP13 프레임 | 129 | 15 |
| HTTP 요청 수 | 972 | 5,957 |

패킷 수는 Artex가 3.7배 많지만, HTTP 요청 수는 Cyberstrike가 6배 많습니다. Artex의 패킷 상당수는 전 포트 스캔과 TLS 대용량 전송에서 나왔고, Cyberstrike는 HTTP 요청 자체가 트래픽의 중심이라는 차이가 개요 단계에서 이미 드러납니다.

## Artex 세션 분석

트래픽 구성은 TCP가 384,814프레임으로 사실상 전부이고, 그중 TLS가 약 90MB를 차지합니다. HTTP는 1,960프레임, AJP13(Tomcat 8009 커넥터)이 129프레임 잡혔습니다. UDP 쪽은 DNS·NTP·mDNS·NBNS·DHCP·SNMP·TFTP·RIP·SSDP·RADIUS가 소량씩 섞여 있어, 격리망이 아니라 일반 네트워크에서 캡처됐음을 보여줍니다.

엔드포인트 바이트를 보면 공격 외 트래픽의 비중이 큽니다. 다만 그 "공격 외" 트래픽은 성격이 둘로 갈리므로, 외부 IP는 TLS ClientHello의 출발지 IP와 SNI로 귀속을 확인했습니다.

| IP | 패킷 | 바이트 | 출발지 | 성격 |
|---|---|---|---|---|
| 192.168.6.132 | 299,056 | 140 MB | - | 공격자 |
| 192.168.6.167 | 229,908 | 119 MB | - | 타깃 |
| 104.18.3.115 | 155,220 | 128 MB | 192.168.6.132 | openrouter.ai (LLM 에이전트 추론 트래픽) |
| 210.117.237.2 | 57,520 | 72 MB | 192.168.6.167 | ftp.kaist.ac.kr (타깃 dnf 미러) |
| 34.144.227.243 | 28,001 | 34 MB | 192.168.6.167 | GCP RockyLinux 미러 (타깃 dnf) |

가장 큰 플로우인 104.18.3.115(128MB)는 Cloudflare 대역이라 미러 CDN처럼 보이지만, ClientHello 출발지가 공격자(192.168.6.132)이고 SNI가 `openrouter.ai`입니다. 즉 이 세션을 구동한 LLM 에이전트(artex)가 외부 LLM API와 주고받은 추론 트래픽으로 판단되며, 타깃의 정상 행위도 공격 트래픽도 아닙니다. 반면 210.117.237.2·34.144.227.243은 출발지가 타깃이라 타깃 서버가 패키지 미러에 접속한 통신으로 보입니다.

정찰 단계에서는 공격자가 타깃으로 전 포트 SYN 스캔을 수행했습니다. SYN 패킷 기준 목적지 포트가 65,535개 전부, 총 132,171개로, 전 포트 스캔(nmap `-p-` 등)의 양상입니다. 이 SYN만으로도 전체 패킷의 약 34%이고, 스캔에 대한 RST 응답·재전송까지 더하면 스캔 관련 트래픽이 패킷의 큰 비중을 차지합니다.

공격 도구는 User-Agent로 구분됩니다. `curl/7.88.1` 532건, `Python-urllib/3.11` 367건, `Nmap Scripting Engine` 49건으로, curl과 파이썬 기반 요청이 공격 요청의 다수를 차지합니다(UA는 위조 가능하므로 도구 확정이 아니라 관측값입니다). HTTP 메서드도 GET 877, POST 51 외에 OPTIONS 26, PROPFIND 6, SEARCH 4, HEAD 4, CONNECT 3, TRACE 1로 다양해, 단일 퍼징 도구 위주의 트래픽과는 다른 양상입니다.

타깃으로 보낸 요청 URI는 앞서 작성된 modubank 모의해킹 보고서의 취약 엔드포인트와 대체로 대응합니다. 아래 "대응 취약점"은 각 요청이 그 취약점을 악용했다는 확정이 아니라, 해당 URI가 보고서의 어느 취약 지점에 해당하는지를 매핑한 것입니다.

| 요청 URI | 횟수 | 대응 취약점 |
|---|---|---|
| /bank/transfer/check-account | 379 | Blind SQL Injection |
| /bank/connectivity/check | 65 | OS 명령 주입 |
| /admin | 64 | 예측 가능 세션 ID / 인증 우회 |
| /files/download | 60 | 경로 traversal |
| /uploads/i8cmd.jsp | 41 | 업로드 웹셸(RCE) |
| /mypage/api-key | 32 | API 키 노출 |
| /bank/fx/lookup | 29 | SSRF |
| /manager/html, /manager/html/deploy | 28 | Tomcat Manager WAR 배포 |
| /actuator/env·heapdump·mappings·beans… | 다수 | Spring Actuator 정보 노출 |
| /app/app.jsp | 5 | 배포한 WAR 웹셸 |

응답 분포는 200 OK 744, 302 Found 113, 500 Internal Server Error 54, 400 Bad Request 32, 404 Not Found 25, 401 Unauthorized 23, 403/405/501 소수입니다. 500 응답은 명령 주입·SQL 주입 시도 구간과 시각적으로 겹칩니다. 다만 상태코드 200은 HTTP 처리 결과일 뿐 공격 성공과 1:1로 대응하지 않으므로, 200이 다수라는 사실만으로 침해 성공을 단정하지는 않습니다. 실제 성공 여부는 뒤의 콘텐츠 타입·응답 본문에서 다시 봅니다.

## Cyberstrike 세션 분석

트래픽 구성은 Artex와 반대로 HTTP가 전면에 나옵니다. HTTP 11,898프레임, 그중 응답 본문(data-text-lines)만 약 10.5MB로, 요청·응답 왕복 자체가 트래픽의 중심입니다. TLS는 54MB, AJP13은 15프레임에 그칩니다.

정찰은 상대적으로 가볍습니다. SYN 스캔 목적지 포트가 1,000개, 총 3,408개로 nmap 기본(top-1000) 스캔 범위입니다. 포트별로는 80번이 1,314건으로 압도적이고 8080·8009·22·3306이 뒤따라, 웹 서비스에 집중했음을 보여줍니다.

공격 도구는 성격이 뚜렷합니다. User-Agent `Fuzz Faster U Fool v2.1.0-dev`(ffuf)가 4,614건으로 전체 요청의 대부분을 차지하고, `curl/8.18.0` 1,253건, `Nmap NSE` 57건 순입니다. HTTP 메서드는 GET이 5,888건으로 98.8%에 달해, 콘텐츠 탐색(디렉터리·파일 브루트포싱)이 세션을 지배했습니다.

이 성격은 응답 분포에서 그대로 확인됩니다. 500 Internal Server Error가 4,643건(응답의 78%), 302 Found 1,130건, 200 OK는 162건입니다. 요청량은 Artex의 6배지만 200 응답은 162건으로 Artex(744건)의 약 1/5 수준이라, 넓게 탐색했으나 200으로 돌아온 응답은 적습니다.

타깃 요청 URI에서도 두 갈래가 보입니다. 하나는 `/mypage/api-key`에 1,117건이 몰린 집중 요청이고, 다른 하나는 `/.git/HEAD`, `/HNAP1`, `/evox/about`, `/robots.txt`, `/sdk`, `/docs/`, `/TODO`, `/readme`, `/favicon.ico` 같은 전형적인 ffuf 워드리스트 항목입니다. 후자는 실제 취약점이라기보다 콘텐츠 탐색 사전에 들어 있는 경로로, 존재 여부를 훑는 스캔의 흔적입니다.

## 서버가 돌려준 응답의 종류 (성공·오류)

공격 요청에 대해 타깃이 실제로 어떤 응답을 와이어에 실어 보냈는지를, 상태코드와 콘텐츠 타입, 대응 URI로 분류했습니다. 두 캡처 모두 HTTP(80·8080) 평문이라 응답 본문이 암호화 없이 남아 있어, 필요하면 응답 내용을 직접 확인할 수 있습니다(본 분석은 상태코드·콘텐츠 타입 집계까지 다루며, 본문 열람은 별도입니다).

Artex의 응답 997건은 성공이 다수이고, 성공 안에서도 콘텐츠 타입이 갈립니다.

| 분류 | 코드 | 콘텐츠 타입 | 건수 | 내용 |
|---|---|---|---|---|
| 성공 – API 데이터 | 200 | application/json | 419 | check-account(SQLi)·connectivity·api-key 등 JSON 응답 |
| 성공 – 화면 | 200 | text/html | 148 | /admin·/bank/dashboard·/login·/manager/html |
| 성공 – 명령·파일 출력 | 200 | text/plain | 115 | 웹셸 RCE 출력(/uploads/i8cmd.jsp), LFI 파일 내용(/files/download) |
| 성공 – Actuator | 200 | actuator v3 json | 33 | /actuator/env·mappings·configprops 등 설정 노출 |
| 성공 – 기타 | 200 | gzip·xml·빈값 | 29 | heapdump gzip 등 |
| 리다이렉트 | 302 | - | 113 | 인증 필요 경로의 /login 바운스 또는 로그인 성공 이동 |
| 서버 오류 | 500 | html·json | 54 | 주입 페이로드가 앱 로직을 깨뜨린 응답 |
| 클라이언트 오류 | 400 | html | 32 | 인코딩·변형 요청 거부 |
| 미존재 | 404 | - | 25 | 경로 탐색 실패 |
| 인증 거부 | 401 | html·json | 23 | /manager/html·/api/v1/accounts/1 인증 전 접근 |
| 기타 | 403·405·501 | - | 6 | - |

text/plain 115건이 특히 눈에 띕니다. 대상 URI가 웹셸(`/uploads/i8cmd.jsp`, `/app/app.jsp`)과 경로 탐색(`/files/download`)이라는 점에서, 명령 실행 결과나 읽어낸 파일 내용이 평문으로 돌아온 응답으로 보입니다. 다만 Content-Type만으로 본문 내용을 확정할 수는 없어, 실제 노출 여부는 본문 확인이 필요합니다. application/json 419건은 대상 URI로 보면 SQL 주입 대상(`/bank/transfer/check-account` 379건)과 계좌·API 키 관련 응답이 섞여 있는 것으로 추정됩니다.

Cyberstrike의 응답 5,957건은 성격이 반대로, 오류가 압도합니다.

| 분류 | 코드 | 콘텐츠 타입 | 건수 | 내용 |
|---|---|---|---|---|
| 서버 오류 | 500 | html·json | 4,643 | 존재하지 않는 경로에 404가 아닌 500을 돌려준 것으로 보임 |
| 리다이렉트 | 302 | - | 1,130 | /mypage/api-key 1,113건 등 미인증 리다이렉트 |
| 성공 – 화면 | 200 | text/html | 80 | 응답이 200으로 반환된 페이지 |
| 성공 – 명령 출력 | 200 | text/plain | 42 | /bank/connectivity/check 응답(명령 출력으로 보임) |
| 성공 – 빈값·json·actuator | 200 | 빈값·json·actuator | 40 | - |
| 클라이언트 오류 | 400 | html | 8 | - |
| 미존재 | 404 | html·빈값 | 6 | - |
| 인증 거부 | 401 | html | 4 | - |
| 기타 | 403·501 | html | 4 | - |

500 응답 4,643건의 대상 URI를 보면 `/README`, `/robots.txt`, `/sdk`, `/docs/`, `/fckeditor`, `/games`, `/MANIFEST.MF`, `/makefile`, `/Members` 처럼 ffuf 콘텐츠 탐색 사전에 흔히 들어 있는 경로들입니다. 이런 경로에 500이 집중된 점으로 보아, 타깃이 미존재(또는 미매핑) 경로에 404가 아니라 500을 돌려주고, 퍼징이 훑은 수천 개 경로가 그대로 500으로 쌓인 것으로 보입니다. 다만 각 경로의 실제 존재 여부와 500의 서버측 원인(미들웨어·입력 처리 등)은 응답 본문·서버 로그 없이 단정하기 어렵습니다. 어느 쪽이든 500 폭증 자체는 공격 성공을 뜻하지 않습니다. 같은 맥락에서 302 1,113건도 `/mypage/api-key`를 미인증으로 반복 호출해 로그인으로 리다이렉트된 흐름으로 보여, 성공과는 거리가 있습니다.

정리하면 두 캡처에서 공격 성과로 볼 만한 구간은 공통적으로 200 text/plain(명령·파일 출력으로 보이는 응답)과 200 application/json(데이터 응답)에 모여 있습니다. Artex는 이 200 응답이 744건으로 많고 콘텐츠 타입도 다양한 반면, Cyberstrike는 200이 162건에 그치고 대부분이 미존재 경로에 대한 500·미인증 302입니다. 다만 200 전체를 곧바로 공격 성공으로 환산할 수는 없으므로(로그인 화면 등 정상 응답 포함), 요청량과 실제 성과를 반비례로 단정하기보다 "요청량은 Cyberstrike가 많지만 200으로 돌아온 응답은 Artex가 많다"는 관찰로 둡니다.

## 두 세션의 성향 차이

| 관점 | Artex | Cyberstrike |
|---|---|---|
| 정찰 범위 | 전 포트(65,535) | top-1000 |
| 주 도구 | curl + Python 스크립트 | ffuf(퍼징) |
| 공격 방식 | 취약점별 정조준 | 광역 콘텐츠 탐색 |
| HTTP 요청 | 972 (메서드 다양) | 5,957 (GET 98.8%) |
| 성공(200) 응답 | 744 | 162 |
| 서버 오류(500) | 54 | 4,643 |
| 트래픽 중심 | 포트 스캔 + TLS | HTTP 요청·응답 |

같은 타깃·같은 공격자임에도 두 세션의 성향은 분명히 갈립니다. Artex는 적은 요청으로 취약점에 대응하는 개별 엔드포인트에 집중한 정밀형으로, 다양한 메서드와 특정 URI에 요청이 모입니다. Cyberstrike는 많은 요청을 넓게 보내 공격면을 탐색하는 브루트포스형으로, 대부분이 미존재 경로에 대한 500과 미인증 302입니다. 탐지 관점에서 두 세션은 "다양한 메서드·엔드포인트에 걸친 소량 요청"(Artex)과 "단일 UA의 500·302 대량 발생"(Cyberstrike)이라는 서로 다른 트래픽 지문을 남깁니다. 다만 침해 성공 여부·효율의 우열은 네트워크 집계만으로는 확정하기 어렵고, 여기서는 트래픽 성향 차이로 한정해 봅니다.

## 공격 중에 섞인 정상 앱 사용 행위

두 에이전트는 타깃을 공격하기만 한 것이 아니라, 타깃 애플리케이션을 정상 사용자처럼 쓰는 합법 요청도 함께 보냈습니다. 공격자(192.168.6.132)에서 타깃(192.168.6.167)으로 간 HTTP 요청을 메서드·경로로 분류하면, 공격 페이로드와 정상 기능 사용이 같은 세션 안에 섞여 있습니다.

| 정상 행위 | Artex | Cyberstrike | 성격 |
|---|---|---|---|
| 회원가입 | GET /signup 6 · POST /signup 3 | GET /signup 4 | 가입 페이지 접근(Artex는 POST 제출 포함) |
| 로그인 | GET /login 12 · POST /login 10 | GET /login 5 · POST /login 4 | 로그인 시도(POST 뒤 302 /bank/dashboard 관측) |
| 공개 페이지 열람 | GET / 15 | GET / 21 · /board 8 · /products 5 | 비인증 페이지 접근 |
| 로그인 후 내비게이션 | /bank/dashboard 38 · /mypage 2 | /bank/dashboard 3 | 대시보드·마이페이지 조회 |
| 이체 페이지 | GET /bank/transfer 3 | GET /bank/transfer 3 | 이체 페이지 GET 접근(실제 이체 실행은 미확인) |

Artex는 로그인(POST /login → 302 /bank/dashboard)으로 세션을 만든 정황이 관측되고, 대시보드도 38건 조회합니다. 이후 같은 공격자 출발지에서 SQL 주입·명령 주입·웹셸 요청이 이어집니다. 다만 정상 로그인으로 만든 세션과 공격 요청이 동일 세션인지(쿠키 연속성)는 본 분석의 집계만으로는 확정하지 않고, 정상 기능 사용과 공격이 같은 출발지에서 함께 나타난다는 수준으로 둡니다.

이 "정상 행위 비중"은 공격자가 타깃으로 보낸 전체 HTTP 요청 중 정상 앱 사용에 해당하는 요청의 비율로 셌습니다. 분모는 공격자(192.168.6.132)→타깃(192.168.6.167) HTTP 요청 총수이고, 분자는 일반 사용자도 동일하게 보낼 법한 요청(로그인·회원가입·`/`·`/board`·`/products` 열람·`/bank/dashboard` 조회·`/bank/transfer` 페이지 등)만 집계한 값입니다. Artex는 970건 중 99건이 이에 해당해 약 10%이고, 나머지 약 90%는 스캔·주입·퍼징 같은 공격 요청입니다. check-account에 대한 SQL 주입만 379건이 반복되는 등 공격 요청이 많아, 정상 행위를 분명히 수행함에도 전체에서 차지하는 비중은 10% 수준으로 낮습니다.

Cyberstrike도 로그인·회원가입과 `/`, `/board`, `/products` 열람 같은 정상 행위를 하지만 비중은 훨씬 작아, 5,952건 중 68건으로 약 1%입니다. ffuf 퍼징이 수천 건을 차지하기 때문입니다. 게다가 Cyberstrike에서는 "페이지처럼 보이는" 요청의 상당수가 실제 내비게이션이 아니라 ffuf 워드리스트 탐색(`/robots.txt`, `/.git/HEAD`, `/HNAP1`, `/evox/about`, `/music`, `/SiteMap` 등)이라, 정상 사용과 스캐너 프로빙을 경로만으로 가르기도 어렵습니다. 두 수치 모두 명백히 정상인 요청만 센 보수적 하한이며, 핵심은 "두 에이전트가 정상 행위를 하긴 하되 전체 요청에서 차지하는 비중은 작다(Artex 약 10%, Cyberstrike 약 1%)"는 점입니다.

여기서 탐지상 중요한 지점은 **요청 형태는 정상과 같되 값만 악성인 경우**가 존재한다는 점입니다. 예를 들어 `GET /admin`·`/bank/dashboard`는 세션 식별자(쿠키) 값만 바꿔 타 계정 자원을 조회하면 요청 형태는 정상 조회와 동일하지만 세션 예측·IDOR가 되고, `POST /login`도 `redirect=` 파라미터 값만 외부 도메인이면 형식은 정상 로그인과 같은 오픈 리다이렉트가 됩니다. `/actuator/*` 접근 역시 경로만 보면 상태 점검과 구분되지 않습니다(이 예시들은 일반적 탐지 난점으로, 각 사례의 실제 성립은 파라미터 값·응답까지 확인해야 합니다). 공통점은 공격 에이전트가 정상 기능 사용으로 세션·맥락을 만들고 그 안에 공격 요청을 섞기 때문에, 경로·메서드만으로는 둘을 분리하기 어렵다는 것입니다. 파라미터 값, 세션 식별자 순회, 요청 속도·반복, 응답 크기를 함께 봐야 정상 거래를 유지하면서 공격을 선별할 수 있습니다.

참고로 이 "정상 행위"는 타깃을 향한 것이며, 타깃 서버가 외부로 수행한 동작(RockyLinux dnf 미러 접속으로 보이는 통신, 출발지 192.168.6.167)이나 공격 도구가 LLM 기반이라 발생한 openrouter 추론 트래픽(출발지 192.168.6.132)과는 구분됩니다. 후자 둘은 바이트 비중은 크지만(각각 Artex 약 106MB·128MB) 공격자가 타깃을 상대로 한 요청이 아니므로, 공격 세션 분석에서는 배경으로 분리해 둡니다. 다만 미러 접속이 공격과 전적으로 무관한지, openrouter 통신이 전부 추론인지까지는 호스트 로그 없이 단정하지 않습니다.

## 추론용 LLM 통신량 비교

두 세션 모두 공격을 LLM이 구동하므로, 공격자 호스트(192.168.6.132)에서 openrouter.ai로 나간 TLS는 LLM 추론(프롬프트·응답) 통신으로 판단됩니다. openrouter는 Cloudflare 대역(104.18.2.115·104.18.3.115)에 올라 있고, 해당 흐름의 ClientHello 출발지가 모두 공격자였습니다(프로세스 수준 귀속은 호스트 로그가 있어야 확정됩니다). 암호화돼 있어 개별 HTTP 요청·응답의 경계와 내용은 복호화 없이 알 수 없으나, 방향별 바이트·연결 수·구간 같은 메타데이터는 집계할 수 있습니다.

아래 바이트는 엔드포인트/대화 집계(TCP·IP 헤더·ACK·재전송 포함 전체 프레임 바이트)로, 캡처 개요의 TLS 약 90 MB(TLS 프로토콜 계층으로 분류된 프레임 바이트)와는 집계 계층이 달라 수치가 큽니다. 두 값은 같은 대상을 다른 기준으로 센 것으로, 서로 모순이 아닙니다.

| 지표 | Artex | Cyberstrike |
|---|---|---|
| 추론 대화 바이트(openrouter 엔드포인트 집계) | 약 128 MB | 약 47 MB (41 + 5.8) |
| 패킷 | 155,220 | 42,367 |
| TCP 연결 수 | 1 (지속 유지) | 8 |
| 활성 구간 | 약 1,123초 (캡처 거의 전체) | 약 951초 |
| 캡처 총량 대비 | 248 MB 중 51.6% | 96 MB 중 48.8% |
| 공격자↔타깃 통신량(참고) | 약 12 MB | 약 29 MB |
| 추론 : 공격자↔타깃 바이트 비 | 약 10.7 : 1 | 약 1.6 : 1 |
| 평균 처리율(대화 바이트/활성 구간) | 약 117 KiB/s | 약 50 KiB/s |

바이트 총량은 Artex의 추론 대화가 Cyberstrike의 약 2.7배입니다. 두 캡처 모두 추론 대화가 전체의 절반가량을 차지하는 공통점이 있으나, 공격자↔타깃 통신량 대비 비중에서 차이가 납니다. Artex는 공격자↔타깃 12MB에 추론 128MB로 약 10.7배, Cyberstrike는 47MB 대 29MB로 약 1.6배입니다. 다만 TLS 바이트에는 컨텍스트·도구 출력·재전송·프로토콜 오버헤드가 함께 포함되므로, 바이트량을 곧바로 "판단의 양"으로 등치하기는 어렵습니다. 관측 가능한 사실은 "Artex가 더 적은 공격자↔타깃 요청에 훨씬 많은 LLM 통신을 수반했고, Cyberstrike는 ffuf 사전 기반 대량 요청으로 공격자↔타깃 통신 비중이 상대적으로 높다"는 정도입니다. (공격자↔타깃 통신에는 앞서 본 정상 기능 요청도 섞여 있어, 이 구간 전체를 공격 트래픽으로 보지는 않습니다.)

연결 패턴도 다릅니다. Artex는 openrouter와 단일 TCP 연결을 캡처 거의 전 구간 유지하며 그 위로 128MB를 주고받은 반면, Cyberstrike는 8개의 개별 연결로 나눠 통신했습니다. 네트워크 관점에서 두 경우 모두 "내부 호스트가 외부 LLM 엔드포인트와 장시간·대용량 TLS를 유지"하는데, 이는 LLM 구동 자동 공격 에이전트에서 나타날 수 있는 트래픽 특징입니다. 다만 두 사례만으로 일반화하기는 이르고, 정상적인 LLM 사용이나 다른 자동화 도구도 유사한 통신을 만들 수 있어, 단독 지표보다는 공격 트래픽과 결합해 볼 보조 신호로 보는 편이 안전합니다.

## 정리

이번 분석에서 확인된 핵심은 두 가지입니다. 첫째, 같은 타깃을 대상으로 한 두 세션의 트래픽 성향이 다릅니다. Artex는 전 포트 스캔 뒤 curl·파이썬 스크립트로 개별 취약 엔드포인트에 집중(다양한 메서드·소량 요청), Cyberstrike는 top-1000 스캔 뒤 ffuf로 광역 콘텐츠 탐색(단일 UA·500 대량)이라는 서로 다른 트래픽 지문을 남깁니다. 침해 성공의 우열은 네트워크 집계만으로 단정하지 않습니다. 둘째, 두 에이전트 모두 타깃을 상대로 회원가입·로그인·페이지 열람 같은 정상 앱 사용을 공격과 함께 수행합니다. 공격자→타깃 요청 중 명백한 정상 앱 사용 비율은 Artex 약 10%(970건 중 99건), Cyberstrike 약 1%(5,952건 중 68건)로 작지만, 세션 예측·오픈 리다이렉트처럼 요청 형태는 정상과 같되 값만 악성인 경우가 있어 경로·메서드만으로는 공격과 정상을 가를 수 없습니다.

다음 단계로는 이 공존 구조를 탐지 룰 검증에 활용할 수 있습니다. 두 세션의 상반된 지문(소량·다엔드포인트 요청 대 단일 UA·500 대량)을 각각 상관 룰로 분리하고, 정상 외형 공격은 파라미터 값·세션 식별자 순회·요청 속도·응답 크기를 함께 보는 조건으로 선별해, 정상 거래를 유지하면서 공격을 걸러내는 정밀도를 로컬 범위에서 점검할 수 있습니다. 배경 트래픽(타깃의 미러 접속, 공격자 호스트의 openrouter 통신)은 용도를 확인한 뒤 분리하되, 검증 없이 일괄 제외하면 공격 관련 활동을 놓칠 수 있으므로 범위를 좁혀 다룹니다.
